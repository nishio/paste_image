# 画像を検索可能にする

個人用 Gyazo の最大の不満であり、LLM Wiki への接続点。

## 問題

画像置き場は貯まるほど価値が下がる。**貯めた画像を見つけられない**から。
Gyazo を何年使っても「あのスクショ」に辿り着けないのは、
バイナリに検索の取っ掛かりが無いことに尽きる。

LLM から見ても同じで、画像だけ置いてあるストレージは LLM にとって空に等しい。

## 方針

画像に対する**テキスト**を同じ item に持たせる。種類は 3 つ。

| 列 | 中身 | 誰が書くか |
|---|---|---|
| `body` | 自分のメモ | 人間(Phase 2) |
| `ocr_text` | 画像内の文字 | 機械(Phase 3) |
| `caption` | 画像の説明 | LLM(Phase 3) |

スクリーンショットは**文字が写っている**ことが多いので、OCR の費用対効果が高い。
写真が主ならキャプション側が効く。

検索は D1 の FTS5 で、この 3 列 + `title` を横断する。
仮想テーブルは Phase 3 まで作らない([[item-not-image]] の「やりすぎないための線引き」)。

## 未決

- OCR / キャプションを Workers AI でやるか外部 LLM API でやるか
  - Workers AI は同じ Worker 内で完結するが、精度は外部 API に劣る
  - 日本語のスクショが主なので、日本語 OCR の精度が選定の軸になる
- アップロード時に同期でやるか、キューに入れて非同期でやるか
  - CPU 10 ms([[cloudflare-workers-constraints]])を考えると同期は無理。
    Queues か Cron で後追いする形になる
