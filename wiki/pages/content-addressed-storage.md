# content-addressed storage

blob の保存先 key を内容の sha256 にする。paste_image では R2 の `blobs/<sha256>`。

## 得られるもの

- **重複排除が無料で付いてくる。** 同じ画像を2回上げても R2 への PUT は1回。
  API は `deduped: true` を返す。スクショを貼り直す運用では地味に効く
- **`immutable` キャッシュが正当化される。** key が内容で決まるので、
  同じ URL の中身が変わることが原理的にない。
  `Cache-Control: public, max-age=31536000, immutable` を自信を持って付けられる
- **ETag がタダで手に入る。** hash をそのまま ETag にできる

## 代償

**削除が参照カウントになる。** item と blob が 1:1 でなくなるので、
item を消しても blob を消してよいとは限らない。

paste_image の削除は、item を論理削除したあと
「同じ `blob_hash` を持つ生存 item が 0 件か」を数えて、0 なら R2 から消す。
単一ユーザの前提なので競合は無視している。複数ユーザに広げるなら、ここは正しくない。

## 副産物: 同じ画像を貼ったページが繋がる

同じ画像は必ず同じ hash になるので、
**「この画像が貼られているページ一覧」が検索なしで引ける**。
`blob_hash` に index を張ってあるので、クエリ1本で出る。

これは Cosense 側で長く欲しがられていた機能に対応する:

> ページAとページBに同じ図を貼ったらリンクが繋がるべきではないか
> — https://scrapbox.io/nishio/同じ図を貼ったらつながるべきでは (2024-09-12)

そこでの議論では「Gyazo の画面で『この画像が貼られてるページ』一覧が出るといいのか」
「プロジェクトによらず出るといいな」という話になっていた。
画像置き場の側が content-addressed なら、**プロジェクト横断で成立する**のがポイントで、
Wiki 側の実装に依存しない。

Phase 2 以降で `GET /api/blobs/{hash}/items` として露出させる予定。スキーマ側の準備は済んでいる。
